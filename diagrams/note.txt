RESULTS 

Overview
This section reports confirmed results gathered from real hardware testing and Vivado implementation reports for all four Reconfigurable Modules (RMs): rm_bare (baseline, no countermeasure), rm_desync (desynchronization), rm_masking (first-order Boolean masking), and rm_dummy (dummy-round insertion). All four RMs were built, flashed to on-board Quad-SPI flash at their assigned addresses, and tested via autonomous, button-triggered Dynamic Function eXchange (DFX) reconfiguration, no host computer or JTAG cable involved in the swap itself.

Note on scope: the security half of the originally planned security-efficiency metric (CPA-based traces-to-key-recovery) was not completed this period. A simulation-based approach (per-trial switching-activity capture) was attempted but not completed within the project timeline. The results below cover functional correctness, resource overhead, timing, and power: The "overhead" half of the tradeoff, plus correctness verification.

Open item: rm_desync cycle-count variance

rm_desync's intended randomized delay (1–15 cycles, meant to vary per encryption) does not produce observable variance in on-chip AXI-timer cycle-count measurements - all RMs, including rm_desync, report an identical, constant cycle count across every trial tested (fixed-vector and random-input alike).

This was searched about at the netlist level. The random-delay source (a 32-bit Fibonacci LFSR, implemented after an earlier free-running-counter-based version was found and replaced) was confirmed genuinely free-running: its clock-enable is tied directly to logic-1 (VCC), meaning it advances every clock cycle with no gating. The register that latches whether the delay logic is actively waiting (waiting_reg) was similarly confirmed free-running and correctly driven.

However, the register that actually holds the delay value used by the countdown logic (delay_target_reg) has a clock-enable driven by a distinct internal signal (delay_cnt11_out), not tied to a constant. This signal's own source was not traced further. The most likely explanation for the observed flat timing, based on this asymmetry, is that delay_target_reg is only re-sampled from the free-running LFSR once, at RM load / reset, rather than once per individual encryption. If so, the LFSR's genuine randomness would continue to evolve in the background between encryptions, but never propagate into the value that actually controls the countdown, since it is never re-latched after the initial sample. This would produce exactly the observed symptom: a fixed, non-zero-but-constant delay per RM session, invisible to repeated-trial timing measurement within that session.

Theory: How Power and Timing Attacks Work

What a "trace" is: every time the chip encrypts something, you can record one measurement of what it was doing at that moment, either how much power it used, or exactly how long it took. That one recording is called a trace. To attack the key, you need many traces (hundreds or more), not just one.

Why the attacker doesn't attack all 128 bits at once: the key is 16 bytes. Instead of guessing all 128 bits together (an impossibly large number of combinations), the attacker guesses one byte at a time, each byte only has 256 possible values, which is easy to try all of. Do this 16 times, once per byte, and you've recovered the full key.

The actual trick, for both power and timing: for one key byte at a time, the attacker tries all 256 possible values. For each guess, they calculate what the measurement (power or timing) should look like if that guess were correct. Then they compare that prediction against the real measurements collected across many runs. The correct guess's prediction keeps matching, run after run. Wrong guesses only match by chance sometimes, and mostly don't. With enough traces, the correct guess clearly stands out.

Power version: the amount of current the chip draws changes slightly depending on what data it's processing internally. Measuring that current over many encryptions gives the power traces used in the comparison above.

Step 1: Run encryption N times, different plaintext each time
Step 2: Record power draw during each run  ->  N power traces
Step 3: For ONE key byte, try a guess (0-255) 
Step 4: Predict expected power for that guess, per trace 
Step 5: Compare predicted list vs real trace list  ->  correlation score 
Step 6: Repeat Steps 3-5 for all 256 guesses 
Step 7: Highest correlation score = correct key byte 
Step 8: Repeat Steps 3-7 for all 16 key bytes  ->  full 128-bit key

XOR lets the attacker instantly work out exactly what value would go into the S-box for any guessed key byte, just from the known plaintext, giving them a concrete number to predict and check against the real chip measurements one guess at a time.
This works because of a basic property of XOR: if you know any two of the three values in A XOR B = C, you can always work out the third one exactly, with simple arithmetic, no guessing, no ambiguity. (self-inverse of itself)

Correlation (Pearson correlation is used here) is calculated by checking, trace by trace, whether the predicted value and the real measurement are both above-average or both below-average at the same time, if they consistently move together across all 200 traces, the correlation score comes out high; if not, it stays near zero.

Example Power version

Say the attacker has collected 200 traces (200 different plaintexts, same secret key, 200 power readings recorded).

Focus on key byte #1. Two of the 256 possible guesses, worked out

Guess 0x00 (wrong)	Guess 0x2B (the real key byte)
Trace 1: plaintext byte 0x32	0x32 XOR 0x00 = 0x32 → S-box → count 1-bits → predict 5	0x32 XOR 0x2B = 0x19 → S-box → count 1-bits → predict 3
Trace 2: plaintext byte 0x9F	0x9F XOR 0x00 = 0x9F → predict 6	0x9F XOR 0x2B = 0xB4 → predict 4
... (198 more traces, same process)	...	...
Correlate all 200 predictions against the 200 real power readings	score = 0.04 (essentially no relationship)	score = 0.63 (strong, consistent relationship)

Since only the real key byte would make these predictions consistently line up with actual chip power draw across 200 different, unrelated inputs, 0x2B is taken as the correct value for that byte.

Timing version: even though every encryption runs the same math, tiny real timing differences can appear, for example, an internal lookup step running very slightly faster or slower depending on the specific value involved. These differences are far too small to notice by eye but are consistent enough for the same guess-and-compare method to work, using precise timing measurements instead of power.

Step 1: Run encryption N times, different plaintext each time
Step 2: Time each run precisely  ->  N timing measurements
Step 3: For ONE key byte, try a guess (0-255)
Step 4: Predict expected timing for that guess, per trace
Step 5: Compare predicted list vs real timing list  ->  correlation score
Step 6: Repeat Steps 3-5 for all 256 guesses
Step 7: Highest correlation score = correct key byte
Step 8: Repeat Steps 3-7 for all 16 key bytes  ->  full 128-bit key
